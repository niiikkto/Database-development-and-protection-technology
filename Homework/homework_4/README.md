## Задача 1. Запрос без индекса

Запрос возвращает 33 записи (`countDocuments` с тем же фильтром даёт 33).
План: `COLLSCAN` внизу и `SORT` над ним; `nReturned = 33`, `totalDocsExamined = 1200`,
`totalKeysExamined = 0`. Document Efficiency — 2,8 %.

Индексов, кроме `_id_`, в коллекции нет, и по другому пути найти записи сервису `payments`
с уровнем `error` и временем больше 500 мс сервер не может: ему приходится прочитать все 1200
документов и применить фильтр к каждому. Отобранные 33 записи он потом сортирует по `ts`
в памяти, потому что готового порядка у него нет.

## Задача 2. Индекс по правилу ESR

Разбор запроса:

- **E (равенство):** `service: "payments"` и `level: "error"`;
- **S (сортировка):** `ts`;
- **R (диапазон):** `duration_ms: { $gt: 500 }`.

Индекс строится в порядке E, S, R:

```
db.events.createIndex({ service: 1, level: 1, ts: -1, duration_ms: 1 })
```

Новый план: `IXSCAN` → `FETCH`, возвращено те же 33 документа, просмотрено 33 документа и
43 ключа. Число просмотренных документов уменьшилось в 1200 / 33 ≈ 36 раз.

Шаг `SORT` исчез потому, что равенства по `service` и `level` сужают индекс до одного
непрерывного участка, а внутри него записи уже лежат по `ts` в нужном порядке (по убыванию).
Сервер читает участок подряд и получает готовый порядок, досортировывать нечего.
Ключей (43) больше, чем документов (33), потому что `duration_ms` стоит в индексе последним:
сервер просматривает весь участок `payments` + `error` (43 записи), проверяет условие
по ключам и читает с диска только документы, которые подошли (33).

## Задача 3. Порядок полей

| Индекс | Порядок | Вернулось | Документов | Ключей | Шаги |
| ------ | ------- | --------- | ---------- | ------ | ---- |
| нет | — | 33 | 1200 | 0 | COLLSCAN → SORT |
| `service, level, ts, duration_ms` | E, S, R | 33 | 33 | 43 | IXSCAN → FETCH |
| `duration_ms, service, level, ts` | R, E, S | 33 | 33 | 378 | IXSCAN → SORT → FETCH |
| `service, level, duration_ms, ts` | E, R, S | 33 | 33 | 33 | IXSCAN → SORT → FETCH |

**Почему в варианте А просмотрено 378 ключей.** Первым в индексе стоит диапазон
`duration_ms > 500`. Индекс отсортирован по этому полю, поэтому сервер проходит весь участок
«дольше 500 мс», а в него попадают события всех сервисов и всех уровней, и только внутри
участка отбирает `payments` и `error`. Из 378 просмотренных ключей пригодились 33 (Index
Efficiency около 8,7 %), а сортировка по `ts` всё равно идёт в памяти.

**Почему в варианте Б остался шаг `SORT`.** Поле сортировки `ts` стоит после диапазона.
Внутри участка, выбранного диапазоном по `duration_ms`, записи лежат в порядке `duration_ms`,
а не `ts`, поэтому порядок по `ts` индекс не обеспечивает и сервер досортировывает результат
отдельным шагом. Число ключей при этом самое маленькое (33), но стоимость сортировки оно
не учитывает.

**Вывод.** В рабочей базе я оставил бы индекс по ESR (`service, level, ts, duration_ms`).
Он просматривает чуть больше ключей, чем вариант Б (43 против 33), зато даёт готовый порядок
без отдельной сортировки. Сортировка в памяти ограничена 100 мегабайтами, и на реальном
журнале запрос с вариантом Б упал бы с ошибкой, а при росте коллекции вариант А
просматривал бы всё больше ненужных ключей.

## Задача 4. Индекс без подсказки

Запрос: `db.events.find({ level: "error" }).sort({ duration_ms: -1 }).limit(10)`.

Без индекса: возвращено 10, просмотрено 1200 документов, 0 ключей, шаги `COLLSCAN` → `SORT`
(Document Efficiency меньше процента).

Разбор по ESR: **E** — `level`, **S** — `duration_ms`, диапазона нет, поэтому в индексе два поля:

```
db.events.createIndex({ level: 1, duration_ms: -1 })
```

С индексом: возвращено 10, просмотрено 10 документов и 10 ключей, шаги `IXSCAN` → `FETCH` →
`LIMIT`. Ошибок в коллекции 180, но индекс хранит их уже в порядке убывания `duration_ms`:
сервер входит в участок `level = "error"`, берёт первые десять записей и останавливается
благодаря `LIMIT`, остальные 170 он не читает.
